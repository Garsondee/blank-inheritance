# Blank Inheritance (空白相続, Kuuhaku Souzoku) — Project Notes for Claude Code

Starfinder Second Edition campaign: six players, one GM, each player running a level-1 "kid" and a Frame (mech) PC starting at level 12. Full design context lives in [design/design-bible.md](design/design-bible.md) (the original pitch, unchanged) and [design/campaign-arc.md](design/campaign-arc.md) (everything that's emerged since — read both; the arc doc corrects one thing the original text got wrong once the full 8-level shape became clear, namely that Frames *do* level up past the opening arc).

## What this repo is

The campaign's source of truth, stored as JSON under `/data` so it can eventually be synced into and out of Foundry VTT with a dedicated tool (not built yet — see [ROADMAP.md](ROADMAP.md)). The prose design bible is the narrative reference; `/data` is a structured extraction of the same material, meant to be edited directly and kept in sync with it by hand for now.

## Directory structure

- `design/design-bible.md` — full original design document, verbatim. Leave it untouched even when later decisions supersede something in it (see `campaign-arc.md`'s Frame-leveling note for an example) — it's the historical pitch, not a living doc.
- `tools/battle-simulator/` — a standalone, legality-enforcing combat simulator for the scale-and-chassis ruleset (real d20s via a seeded PRNG, a rules engine that rejects illegal moves rather than trusting the AI/scenario not to propose them, battle logs consumed by an Artifact scrubber UI). Not part of the Foundry module; a design-validation tool for testing tactical approaches before committing numbers. Its rules engine was adversarially tested by five independent agents (2026-08-22) — see `test/battle-simulator/` for the resulting regression suite and `tools/battle-simulator/engine/*.mjs`'s own fix comments for what each one found. This is the first real piece of ROADMAP.md #3 (the encounter simulator), pulled forward and scoped to this campaign's own ruleset rather than general SF2E. `tools/battle-simulator/ground-layer/` extends this to the personnel scale: the five non-piloting kids in `data/subsystems/day-1-ground-layer.json` now roll real d20s against real stat blocks (`tools/battle-simulator/data/kid-fixtures/`) to decide whether/when the Interdiction Field actually breaks, instead of a scripted assumption — kept in its own directory on purpose, never importing from `engine/`'s Frame-scale comparisons, per the scale-separation rule below. Distances run at 10x PF2e/SF2e's default grid (design doc §14f) — a reskin, not a rebalance, since every Speed/range scaled with it; combatants deploy together at Round 0 rather than trickling in on an authored schedule, initiative is a real roll (vehicles use Reflex, the Frame is deliberately worse at it — "most Frames are lumbering"), and every turn's action-point spend is checked in code (`accountForActions()` throws if it doesn't add up) and shown on a per-combatant character-sheet panel in the replay UI.
- `tools/character-builder/` — the real SF2E level-1 chargen process (`derive.mjs`, grounded in `reference/srd/player-core/64-character-creation.json`'s actual steps, cited by page), plus a pregen-borrowing shortcut (`extract-pregen.mjs` + `tools/pack-extractor/` reads Foundry's shipped compendium packs — LevelDB write-ahead logs — directly) used to build the kid-fixtures above. Both paths matter: the shortcut is fast, the derivation engine is what makes it verifiable (its output is tested against every Player Core class pregen's own published HP total) and is what the real six kids' character creation should eventually run through too.
- `design/scale-and-chassis.md` — **accepted** (see `ideas/entries/scale-and-chassis-model.json`) proposal for the campaign's hardest mechanical problem: how level-1 kids and level-12 Frames share a battlefield without SF2E's bounded-accuracy maths breaking. Two hard-separated scales, three legal interfaces between them, SF2E's real vehicle rules as a second chassis type, three fully-statted level-12 chassis, worked maths throughout. Read this before designing anything that puts a kid and a Claimant on the same map.
- `design/campaign-arc.md` — everything design-level that's emerged since the original pitch: the 1950s tone pivot, the 8-level arc shape, theme statement, evolving mechanics threads not yet locked into `data/campaign/config.json`. This is the living design doc; update it as the campaign keeps growing.
- `data/schema/*.schema.json` — JSON Schema (draft 2020-12) contract for every entity type; see "Schema architecture" below. Not currently enforced by any validator — they exist as documentation and as the future sync tool's contract. Keep them in sync with the data files by hand.
- `data/campaign/` — singleton config/reference files: `overview.json` (pitch, system notes), `config.json` (Resonance/Bleed/Frame economy/Time Economy/Contact Pool/False Contact numbers), `ground-roles.json`, `gm-notes.json`, `open-questions.json`, `naming-placeholders.json`.
- `data/characters/kids/`, `data/characters/frames/` — one JSON file per PC, each a full SF2E character sheet (kid.schema.json / frame.schema.json). Still empty: none of the six real kids or six real Frames have been created. That's the next collaborative/creative step, not something to pre-generate — the six *synthetic* kid statblocks in `tools/battle-simulator/data/kid-fixtures/` (reflavoured SF2E pregens, one per class, clearly marked "TEST FIXTURE... not one of the six real kids") are simulator ingredients, not a proposal for who they are, exactly like `makeReferenceFrame()` already was for the Frame side.
- `data/npcs/` — the Directorate's three poles (Commander, Caretaker, Transparency Advocate). Unnamed placeholders. Purely narrative unless one ever needs to roll dice — see npc.schema.json's optional `statblock`.
- `data/factions/directorate.json` — the organisation itself.
- `data/antagonists/claimants/claimant-guidelines.json` — build rules and lore for Claimants (not individual stat blocks — none exist yet; new Claimant instances are sibling files here using creature.schema.json). `data/antagonists/the-watcher.json` — the long-arc second antagonist.
- `data/episodes/` — the hand-placed opening arc (Day 1, Days 2-5, Day 6). Day 7 onward is procedural (the Contact Pool), not scripted, so it has no episode file. A scene can link out to `encounterRef`/`challengeRefs`/`subsystemRef` once those exist.
- `data/hangar/legacy-units.json` — the legacy-Frame graveyard, currently empty.
- `reference/srd/` — a local mirror of 205 Starfinder 2E SRD rules articles (Archives of Nethys), for grounding mechanical writing in accurate rules. Not campaign data, not synced to Foundry. See [reference/README.md](reference/README.md) for scope and conventions.
- `reference/tables/` — pure numeric data extracted from the SRD mirror (DC-by-level, degree-of-success math, encounter XP budgets, treasure-by-level), meant for a future encounter/challenge validator to consume directly rather than re-parsing rules prose.
- `ideas/` — tracked ideas at every stage from raw thought to shipped (status: new/wishlist/accepted/in-progress/done/rejected). See [ideas/README.md](ideas/README.md) before adding to it or treating anything in `design/`/`data/` as settled just because an idea file references it — an idea's status is the actual signal, not its presence.
- `artwork/`, `audio/` — raw asset intake libraries (images, audio), **gitignored**, large. Both have an `in-tray/` drop zone; files only move to an organized location once assigned to a specific use, to avoid double-using the same asset. See the `asset-review-pipeline` idea in `ideas/entries/` for the intended workflow (AI-cataloged, human-confirmed, then organized/compressed) — not built yet, currently just the raw trees.

## Schema architecture

- `data/schema/common/sf2e-common.schema.json` holds shared SF2E building blocks as `$defs` (proficiency ranks, ability modifiers, saves, skills, speed, strikes, spellcasting, conditions, feats, etc.) — referenced via `$ref` from the entity schemas below rather than duplicated. It's pure SF2E mechanics; campaign-specific concepts (Resonance, Anchors, Bleed) never belong in it.
- **`pcStatblock`** (in sf2e-common) = the full player-character sheet shape. Used by both `kid.schema.json` and `frame.schema.json`, since a Frame is explicitly built as "a full PC using a standard SF2E class" (design bible) — same underlying shape, different fixed level and campaign overlay.
- **`combatStatblock`** (in sf2e-common) = the monster/NPC stat block shape (flat AC, authored skill mods, no chargen fields) — different from a PC on purpose, per GM Core's own creature-building rules. Used standalone by `creature.schema.json` (Claimants, any other monster) and optionally embedded as `npc.schema.json`'s `statblock` field for the rare NPC that needs to fight.
- `subsystem.schema.json` — GM Core-style victory-point subsystems (Victory Points, Influence, Research, Chases, Infiltration, Hacking, or homebrew). One shared shape (pools, obstacles, thresholds) plus a `subsystemSpecific` bag for what genuinely doesn't generalize (Hacking's DC-modifying vulnerabilities, Infiltration's objective/obstacle hierarchy and Edge Points, Chases' per-obstacle point reset). Don't force a Hacking or Infiltration instance into the plain-pool shape if it isn't one — check `subsystemSpecific` first.
- `challenge.schema.json` — lighter-weight than a subsystem: one or a few DC'd checks with no persistent point pool. Fits Ground Role checks, Anchor Time scenes, one-off skill gauntlets.
- `encounter.schema.json` — a combat encounter's participant list and XP-budget inputs, separate from challenge/subsystem since it uses SF2E's level-relative XP math (`reference/tables/encounter-and-rewards-math.json`) instead of DC'd checks.
- None of this is validated by tooling yet (see ROADMAP.md #1) — treat the schemas as the contract to hand-conform data files to, and keep new fields flowing back into `sf2e-common` when two entity schemas would otherwise duplicate the same shape.

## Conventions

- One JSON file per entity, filename = `id` field (kebab-case), e.g. `data/npcs/commander.json` has `"id": "commander"`.
- Every data file has a `"$schema"` field with a relative path to its schema in `data/schema/` — most editors (VS Code included) will validate and autocomplete against this automatically.
- `null` means "not yet decided," not "empty/unused." A lot of this document is deliberately unresolved — see `data/campaign/open-questions.json` and `data/campaign/naming-placeholders.json`. When a field is null because of a tracked open question, it carries an `openQuestionRef`/`namingPlaceholderRef` pointing at the relevant entry.
- Cross-references between entities are plain string ids (e.g. a kid's `framePilotedRef`), not nested objects — keep entities independently loadable, since that's how they'll eventually map to separate Foundry documents.

## Rules Reference

`reference/srd/` mirrors the SF2e SRD (Galaxy Guide, Player Core, GM Core, Alien Core minus Pact Worlds) — every procedural/mechanical rule, not the item/spell/creature catalogs. Check it before writing anything that leans on specific SF2e mechanics: Frame ability-band assignments, GM adjudication calls, Claimant stat blocks, encounter design, skill DCs. It's more reliable than general knowledge of the system, since exact numbers and wording matter here. See [reference/README.md](reference/README.md) for full scope, structure, and a note on a few files with intentional content overlap. `reference/tables/` has the same information pre-extracted into plain numeric JSON for programmatic use.

One confirmed gap as of the last check: no numeric Elite/Weak adjustment deltas were found anywhere in the mirrored GM Core/Alien Core text — see `adjustment` field notes in `sf2e-common.schema.json`'s `combatStatblock`. Treat any elite/weak numbers as a GM judgment call, not a verified rule, unless this note has been updated after finding the real table.

## Local Foundry source trees (not in git)

Two large reference trees live at the project root, both **gitignored** — same policy as `reference/`, all three are excluded in `.gitignore` because they're bulk third-party/mirrored material, not this project's own content:

- `gamesystems/sf2e/` — the official Foundry VTT "sf2e" system package (v1.4.1, built off the pf2e codebase — matches the design bible's note that SF2E runs on PF2e's engine). Readable parts: **`template.json`** (~18KB, the Actor/Item data model), **`packs/`** (29 compendium packs — LevelDB, not plain JSON; already extracted once, see below), `lang/en.json`, `templates/` (Handlebars sheets). `sf2e.mjs`/`vendor.mjs` are bundled but beautified (not minified) — directly readable.
- `foundryvtt/` — full Foundry VTT v14.367 application source, **unminified** under `client/`/`common/`, minified under `dist/`, at `foundryvtt/Foundry Virtual Tabletop/resources/app/`.

**Already dug into** — see [design/foundry-technical-reference.md](design/foundry-technical-reference.md) for the condensed, cited findings (file:line for the unminified parts) before re-deriving anything from these trees: file I/O and the module write-back mechanism, every relevant Foundry v14 document schema (Scene's `Level` split, JournalEntryPage, Playlist, etc.), the sf2e Actor/Item data model (including the PC-vs-NPC asymmetry — NPCs store flat totals, PCs derive everything from embedded Items), the `@Check`/`@Damage`/`@Template` inline syntax with real examples pulled from the packs, and the ApplicationV2/hooks/module-manifest APIs. Re-verify against the source trees directly only for something not already covered there, or if targeting a different Foundry/sf2e version.

## Foundry module

`foundry/blank-inheritance/` is the actual module (see its own [README](foundry/blank-inheritance/README.md)) — campaign JSON and module code ship together, WinSCP-synced to the Foundry server as one unit. Design and rationale: [design/foundry-module-design.md](design/foundry-module-design.md). See that doc's §9 staged delivery plan before starting implementation, and don't jump straight to the director's panel / cold-open stages before the core push pipeline works. Stage 1 (deterministic IDs, npc + character Actor generation, Scene with tokens, validation-by-reread) is **built and verified against a live Foundry instance** — 15/15 checks passed 2026-08-22.

**[design/testing-strategy.md](design/testing-strategy.md) is required reading before writing any module code.** It's a standing policy, not a suggestion: pure logic lives in `scripts/core/` and may never touch Foundry globals; the adapter layer stays thin; contract tests verify our output against the local `gamesystems/sf2e/` and `foundryvtt/` trees so a system upgrade fails loudly instead of silently. It also records verified gotchas (template.json inheritance, its partial Item coverage) that will cost real time to rediscover.

## Working on this project

- **Don't resolve open design questions unilaterally.** They're listed in `data/campaign/open-questions.json` because they're the user's creative calls (tone, structure, character agency), not implementation details. Surface them when relevant; update a question's `status`/`resolution` and the fields that reference it only once the user actually decides.
- **Don't invent the six kids/Frames' names, classes, or Anchors.** Character creation is collaborative creative work with the user, not something to fill in to make the roster look complete.
- Mechanical/numeric content (Resonance bands, Bleed, Time Economy, Contact Pool) is locked and safe to treat as authoritative — it's written as concrete rules already, not open questions.
- The Foundry sync/module work now has a real design (see above) and is no longer purely hypothetical, but implementation still hasn't started — check with the user before writing actual module code rather than assuming the design doc is a green light. The encounter simulator (ROADMAP.md #3) remains untouched and long-term.
- **Every feature ships with an automated test, in the same commit.** Not "after," not "when there's time" — a feature without a test isn't finished. This is a direct, explicit instruction from the user ("every feature we build needs an automated test to prove that it's still working three versions from now"), grounded in the observation that projects like this one live or die on sustainable code practice. See [design/testing-strategy.md](design/testing-strategy.md) for the tiers, the tooling choice (`node --test`, zero dependencies on purpose), and the rules. Every bug found becomes a regression test at the moment it's fixed.
- **Check `ideas/entries/` before starting speculative new work.** A lot of forward-looking scope (asset pipeline, mech classification, audio system, UI panel, antagonist structure, etc.) is already captured there with a real status — don't re-propose or re-decide something that's already `accepted` there, and don't start building something still sitting at `new` without checking whether it's actually been prioritized.
