# Blank Inheritance (空白相続, Kuuhaku Souzoku) — Project Notes for Claude Code

Starfinder Second Edition campaign: six players, one GM, each player running a pilot plus their machines (a Frame, a vehicle or both), all sharing one level that starts at 1 and advances in lockstep (settled 2026-09-20). **The story lives in one place: `canon/`** (the filing rules at the top of [canon/README.md](canon/README.md); the whole adventure on one timeline with `npm run timeline`; `/plot` before writing about it, `/lore` to file what Ingram says). Any story told elsewhere, in this file included, is old material: search it for ideas, never cite it. Design principles live in [design/campaign-arc.md](design/campaign-arc.md). [design/design-bible.md](design/design-bible.md) is the original pitch, kept frozen: much of its mechanics (level-12 Frames, Resonance, Bleed, the ground roles) has since been cut, so read it for history, not rules.

## What this repo is

The campaign's source of truth, stored as JSON under `/data` so it can eventually be synced into and out of Foundry VTT with a dedicated tool (not built yet — see [ROADMAP.md](ROADMAP.md)). The prose design bible is the narrative reference; `/data` is a structured extraction of the same material, meant to be edited directly and kept in sync with it by hand for now.

## Terminology

Three words, three different things — fixed 2026-09-20 after "Session One"/"Session Two" had drifted into meaning a content chunk everywhere in this repo while the word "session" itself was needed for something else. Get these right; a wrong one is a real error here, not a style choice, and it's fine to correct anyone (including Ingram) who uses one against its definition.

- **Chapter** = a character level. Chapter 2 means the party is level 2, with level-2 Frames and vehicles (they level in lockstep — see `open-questions.json#frame-scale-starting-level`). The `c1`/`c2`/… prefix on an id means the Chapter it belongs to.
- **Episode** = a chunk of authored content. `episode-c1e1-mothers-maiden-name.json` is Chapter 1's first episode; `episode-c1e2-scheduled-exercise.json` is its second. This is what "Session One"/"Session Two" used to mean everywhere in this repo — renamed throughout on 2026-09-20 (`c1s1`→`c1e1`, `c1s2`→`c1e2`, ids, filenames, art and audio stems, and every "Session One"/"Session Two" in prose became "Episode One"/"Episode Two"). `episode.schema.json` was already correctly named; only the ids and the word used in prose were wrong.
- **Session** = a real evening at the table. Doesn't map 1:1 to an episode — one evening might cover several episodes, or stop partway through one. Never appears in an id.

**One deliberately-kept exception:** GitHub epic #140, "Session 0/1 viability," predates this fix and isn't being renamed — it's a live, heavily cross-referenced issue title. Read "Session 0/1" there as shorthand for "Induction (chargen) plus Episode One," not a literal evening or a literal single episode.

## Schema architecture

- `data/schema/common/sf2e-common.schema.json` holds shared SF2E building blocks as `$defs` (proficiency ranks, ability modifiers, saves, skills, speed, strikes, spellcasting, conditions, feats, etc.) — referenced via `$ref` from the entity schemas below rather than duplicated. It's pure SF2E mechanics; campaign-specific concepts never belong in it.
- **`pcStatblock`** (in sf2e-common) = the full player-character sheet shape. Used by both `kid.schema.json` and `frame.schema.json`, since a Frame is explicitly built as "a full PC using a standard SF2E class" (design bible) — same underlying shape, different fixed level and campaign overlay.
- **`combatStatblock`** (in sf2e-common) = the monster/NPC stat block shape (flat AC, authored skill mods, no chargen fields) — different from a PC on purpose, per GM Core's own creature-building rules. Used standalone by `creature.schema.json` (Claimants, any other monster) and optionally embedded as `npc.schema.json`'s `statblock` field for the rare NPC that needs to fight.
- `subsystem.schema.json` — GM Core-style victory-point subsystems (Victory Points, Influence, Research, Chases, Infiltration, Hacking, or homebrew). One shared shape (pools, obstacles, thresholds) plus a `subsystemSpecific` bag for what genuinely doesn't generalize (Hacking's DC-modifying vulnerabilities, Infiltration's objective/obstacle hierarchy and Edge Points, Chases' per-obstacle point reset). Don't force a Hacking or Infiltration instance into the plain-pool shape if it isn't one — check `subsystemSpecific` first.
- `challenge.schema.json` — lighter-weight than a subsystem: one or a few DC'd checks with no persistent point pool. Fits one-off skill checks and short gauntlets.
- `encounter.schema.json` — a combat encounter's participant list and XP-budget inputs, separate from challenge/subsystem since it uses SF2E's level-relative XP math (`reference/tables/encounter-and-rewards-math.json`) instead of DC'd checks.
- None of this is validated by tooling yet (see ROADMAP.md #1) — treat the schemas as the contract to hand-conform data files to, and keep new fields flowing back into `sf2e-common` when two entity schemas would otherwise duplicate the same shape.

## Conventions

- One JSON file per entity, filename = `id` field (kebab-case), e.g. `data/npcs/commander.json` has `"id": "commander"`.
- Every data file has a `"$schema"` field with a relative path to its schema in `data/schema/` — most editors (VS Code included) will validate and autocomplete against this automatically.
- `null` means "not yet decided," not "empty/unused." A lot of this document is deliberately unresolved — see `data/campaign/open-questions.json`, which now also holds every naming gap (merged from `naming-placeholders.json`, 2026-09-19). When a field is null because of a tracked open question, it carries an `openQuestionRef`/`namingPlaceholderRef` pointing at the relevant entry — both field names still work and resolve against the same file.
- Cross-references between entities are plain string ids (e.g. a kid's `framePilotedRef`), not nested objects — keep entities independently loadable, since that's how they'll eventually map to separate Foundry documents.

## Foundry module

`module/blank-inheritance/` is the actual module (see its own [README](module/blank-inheritance/README.md)) — campaign JSON and module code ship together, pushed to the Foundry server as one unit via `tools/module-sync/` (or WinSCP by hand). Consolidated here 2026-09-04/05 from the original `foundry/blank-inheritance/` location (GitHub issue #71) — the manifest `id` deliberately stayed `blank-inheritance`, since every deterministic-id derivation and golden test fixture is keyed to that id. The consolidation briefly renamed the directory itself to something else too, which turned out to be invalid — Foundry's real package loader hard-requires the directory name to exactly match the manifest `id`, rejecting the module outright otherwise (found live 2026-09-05, after it silently broke the module on the server for about a day). Renamed back to match; now enforced by an automated test (`test/tier0-architecture.test.mjs`). Design and rationale: [design/foundry-module-design.md](design/foundry-module-design.md) (now includes a **Safety** section on why world-document writes must go through Foundry's Document API, never raw file access — grounded in real source, learned during the 2026-09-04 server migration). See that doc's §9 staged delivery plan before starting implementation, and don't jump straight to the director's panel / cold-open stages before the core push pipeline works. Stage 1 (deterministic IDs, npc + character Actor generation, Scene with tokens, validation-by-reread) is **built and verified against a live Foundry instance** — 15/15 checks passed 2026-08-22. The production-line roadmap (module build-out, the phone/UI systems, the Claude-to-Foundry content pipeline) is tracked as GitHub epics #102 and #118, milestone "Foundry Module." **Every Actor the pipeline creates carries a Foundry v14 Dynamic Token Ring, automatically (decided 2026-09-18, permanent — `core/generators/token-ring.mjs`, wired into `npc.mjs`/`creature.mjs`/`character.mjs`)**: bronze style (a world setting, not a per-token field — `foundry/token-ring-style.mjs` sets it once on world `ready`), Ring Pulse always on, and the ring's own color identifies faction — vermilion for the Directorate, resonance violet for a Claimant (both colors already meant exactly that in `bi-tokens.css` before this existed), cyan for the player party, amber as the neutral fallback. A circle-cropped subject portrait is optional per actor and resolved by the caller (`foundry/sync.mjs`'s `TOKEN_IMAGE_BY_ID`), never invented by the generators themselves — an uncast NPC still gets a correctly-colored ring around Foundry's own default token art. `tools/token-ring/crop_ring_subject.py` turns an `asset-registry.json`-assigned character portrait into that subject texture (Foundry does not crop or mask the subject itself — confirmed against real v14.367 source — so pre-cropping to an antialiased circle is required, not optional polish). Staged output is gitignored (`module/blank-inheritance/assets/tokens/`, regenerate with that script) and pushed to the server by the same whole-module `tools/module-sync/sync-module.mjs` push as everything else. A portrait existing for a still-placeholder NPC does not make that NPC real enough for `sync.mjs`'s live/production push (`TOKEN_IMAGE_BY_ID` and `REAL_NPC_PATHS` share that same "established," not "placeholder," gate) — six placeholder Directorate-staff portraits assigned the same day are registered and circle-cropped but deliberately held back from the real sync for exactly that reason.

**[design/testing-strategy.md](design/testing-strategy.md) is required reading before writing any module code.** It's a standing policy, not a suggestion: pure logic lives in `scripts/core/` and may never touch Foundry globals; the adapter layer stays thin; contract tests verify our output against the local `gamesystems/sf2e/` and `foundryvtt/` trees so a system upgrade fails loudly instead of silently. It also records verified gotchas (template.json inheritance, its partial Item coverage) that will cost real time to rediscover.

- **A scene's final gate is the Sign-Off, not the Desk — [design/scene-signoff.md](design/scene-signoff.md), designed 2026-09-22 from Ingram's brief, tooling built.** The finding behind it: every grading mechanism this project has built works, and **none of them has ever graded anything** (281 items in `data/`, 0 promoted). The Desk's one-item-one-keystroke model is right for a shed nobody visits and wrong for content that matters, because nobody can grade an NPC in isolation — you grade Nobu by reading the fifteen minutes of Kit Issue, which grades his location and his challenge at the same time. So **the scene is the unit of review, because the scene is the unit of play**, and a scene cleared here carries everything it casts with it. Four passes, one output each, stop between them: **Comprehension** (the whole scene narrated as the GM would run it, verbatim on anything said out loud — a `STOP` here ends the sign-off), **Completeness** (the checklist, required vs recommended, declines named out loud), **Place** (a captioned two-panel map crop sent as an image — Ingram's rule: *"if it doesn't have a location then it's not finished yet"*, and the siting is her call, not mine), **Quality** (at most five ranked findings; obvious fixes applied and shown as done, anything touching meaning/reveal timing/character proposed and waiting). One new status rung, `live`, meaning "ready for actual players to enjoy — it's done." **Two rounds of `FIX` per pass and no more**: the terminator is the point, because a reviewer that can always find something always will. The checklist is versioned data (`data/campaign/signoff-checklist.json`), a seal records the version it cleared, and raising the version marks sealed scenes stale **against the new checks only** — that is how the process is allowed to grow when a session finds a failure state nobody predicted. Trigger with `/signoff`; the board is `node tools/scene-signoff/console.mjs` (also wired into the SessionStart hook). `authoring.status: "live"` and the `review` block have exactly one legal writer, `tools/scene-signoff/seal.mjs` via `seal()` in `core/promote.mjs`, which **refuses any scene whose four passes are not all CLEAR** — so a seal on a conversation that never happened is impossible rather than merely discouraged. This made `authoring.status` the first field with two legitimate owners, split by entity type; see `design/data-ownership.md` §4's new subsection for the rule that allows it.
