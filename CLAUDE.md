# Blank Inheritance (空白相続, Kuuhaku Souzoku) — Project Notes for Claude Code

Starfinder Second Edition campaign: six players, one GM, each player running a level-1 "kid" and a Frame (mech) PC starting at level 12. Full design context lives in [design/design-bible.md](design/design-bible.md) (the original pitch, unchanged) and [design/campaign-arc.md](design/campaign-arc.md) (everything that's emerged since — read both; the arc doc corrects one thing the original text got wrong once the full 8-level shape became clear, namely that Frames *do* level up past the opening arc).

## What this repo is

The campaign's source of truth, stored as JSON under `/data` so it can eventually be synced into and out of Foundry VTT with a dedicated tool (not built yet — see [ROADMAP.md](ROADMAP.md)). The prose design bible is the narrative reference; `/data` is a structured extraction of the same material, meant to be edited directly and kept in sync with it by hand for now.

## Directory structure

- `design/design-bible.md` — full original design document, verbatim. Leave it untouched even when later decisions supersede something in it (see `campaign-arc.md`'s Frame-leveling note for an example) — it's the historical pitch, not a living doc.
- `tools/battle-simulator/` — a standalone, legality-enforcing combat simulator for the scale-and-chassis ruleset (real d20s via a seeded PRNG, a rules engine that rejects illegal moves rather than trusting the AI/scenario not to propose them, battle logs consumed by an Artifact scrubber UI). Not part of the Foundry module; a design-validation tool for testing tactical approaches before committing numbers. Its rules engine was adversarially tested by five independent agents (2026-08-22) — see `test/battle-simulator/` for the resulting regression suite and `tools/battle-simulator/engine/*.mjs`'s own fix comments for what each one found. This is the first real piece of ROADMAP.md #3 (the encounter simulator), pulled forward and scoped to this campaign's own ruleset rather than general SF2E. `tools/battle-simulator/ground-layer/` extends this to the personnel scale: the five non-piloting kids in `data/subsystems/day-1-ground-layer.json` now roll real d20s against real stat blocks (`tools/battle-simulator/data/kid-fixtures/`) to decide whether/when the Interdiction Field actually breaks, instead of a scripted assumption — kept in its own directory on purpose, never importing from `engine/`'s Frame-scale comparisons, per the scale-separation rule below. **Decided 2026-09-02 (design doc §57): that separation is about the *rules* of mixing kids and Frames on one battlefield, not about the AI — there is to be ONE combat AI (decision layer, search, evaluator) serving both scales through a scale-parameterized engine interface; `personnel-engine/` and `engine/` must not keep two copies of `decide()`/`evaluateState`. The roadmap for that AI lives in GitHub issues (epic #3, milestone 1).** Distances run at 10x PF2e/SF2e's default grid (design doc §14f) — a reskin, not a rebalance, since every Speed/range scaled with it; combatants deploy together at Round 0 rather than trickling in on an authored schedule, initiative is a real roll (vehicles use Reflex, the Frame is deliberately worse at it — "most Frames are lumbering"), and every turn's action-point spend is checked in code (`accountForActions()` throws if it doesn't add up) and shown on a per-combatant character-sheet panel in the replay UI.
- `tools/character-builder/` — the real SF2E level-1 chargen process (`derive.mjs`, grounded in `reference/srd/player-core/64-character-creation.json`'s actual steps, cited by page), plus a pregen-borrowing shortcut (`extract-pregen.mjs` + `tools/pack-extractor/` reads Foundry's shipped compendium packs — LevelDB — directly, both the write-ahead log (`read-pack.mjs`) and the compacted `.ldb` SSTables (`read-table.mjs`, with its own Snappy decoder). Reading the bytes rather than opening the database is deliberate: it never takes LevelDB's exclusive lock and can never write to a tree we don't own. **Reading only the log was the original design and it silently broke** the day LevelDB compacted — the logs went to zero bytes, the reader returned nothing instead of erroring, and 64 tests reported missing pregens that were sitting in the SSTables all along; fixed 2026-09-12) used to build the kid-fixtures above. Both paths matter: the shortcut is fast, the derivation engine is what makes it verifiable (its output is tested against every Player Core class pregen's own published HP total) and is what the real six kids' character creation should eventually run through too.
- `tools/city-map/` — real-data city rendering: OpenStreetMap + GSI Japan DEM in, a styled raster map out. The Python implementation of [design/map-generation.md](design/map-generation.md)'s pipeline; see that doc and the tool's own [README](tools/city-map/README.md) before touching it. Independent of `tools/map-generator/` (Node/JS, procedural terrain — keeps its own role for amplification and offshore bathymetry per that design doc's §9); neither imports the other. Rescued 2026-08-24 out of a session scratchpad into this tested, modular form — `_spike8_reference.py` is the last pre-rescue checkpoint, kept only as the source of truth for page-furniture drawing (labels, cartouche, compass rose, paper texture) not yet ported. Structural core (parsing, sea classification, terrain, tiled rendering), the operation log (`ops/demolish.py`, `ops/construct.py`, `ops/router.py`, `ops/replay.py`, `ops/replay_cache.py`), and a real progress-reporting CLI (`render.py`) are all built and tested against real data — the vertical slice (§ROADMAP #4) shipped: Kobe Airport, Port Island, and Rokko Island all reclaimed by the sea (`returnToSea`), a parametric mech-bunker and three Sentinel Tower structures built with routed access roads and real benched platforms, and a first offshore platform proving reclaim-instead-of-bench works (`is_offshore` detection in `apply_construct`, freeboard elevation, no causeway router yet — `ideas/entries/offshore-construction.json` tracks what's left of that plan). Demolish prunes both `road_graph` and `rail_graph` (railways previously had no graph at all, so a severed bridge over open water couldn't be cascade-pruned); `citymap/rivers.py` tapers river width by Shreve stream magnitude and draws above contours; `render.py`'s hillshade and cast-shadow layers now correctly darken roads and buildings, not just bare ground (buildings draw before their own shadow layer, with each building's own footprint excluded from its own cast shadow). `citymap/ops/replay_cache.py` is the op-log-content-hash-keyed "L3" cache — the L1 world and post-replay World are structurally identical, so it reuses `save_world`/`load_world` unchanged; a render with an unchanged op log skips the whole replay (500s+) entirely. `tools/city-map/editor/` (`python tools/city-map/editor/server.py`, opens at `localhost:8765`) is a local Leaflet-based map editor: pan/zoom the real map, click buildings to flag them for removal, draw arbitrary polygons for new construction sites (on land or in the sea) and 2-point road sketches, submit as one JSON file (`data/map/editor-submissions/`, gitignored) for later processing into real ops (`citymap/editor/siting.py` fits a template into a drawn polygon via a real `apply_construct` dry run, same "propose then verify" method used by hand for the Sentinel Tower sites) — plus a render control panel with live SSE progress (a `: ping` heartbeat keeps the connection alive during a long silent `render_tile` call, or the browser's own reconnect logic restarts the render from scratch, repeatedly, looking like a hang). `ops/demolish.py` also takes a `featureIds` payload (exact-id removal, for the editor's flag-a-building flow) as an alternative to `area`. Tests live in `test/city-map/` (Python stdlib `unittest`, run separately from `npm test`, which stays Node-only and unaffected — `python -m unittest discover -s test/city-map -t test/city-map`, per `tools/city-map/README.md`).
- `tools/module-sync/` — verified push of the Foundry module directory to the live server (checksums both sides independently after upload, reports exactly what matches — never trusts a plain exit code). Replaces manual WinSCP for that half of the content pipeline; see its own [README](tools/module-sync/README.md), GitHub issue #112, and epic #118. Does not touch any live Foundry document — see `design/foundry-module-design.md`'s Safety section for why that's a meaningfully different, much lower, risk level than the in-Foundry Sync step.

Two hard-separated scales, three legal interfaces between them, SF2E's real vehicle rules as a second chassis type, three fully-statted level-12 chassis, worked maths throughout. Read this before designing anything that puts a kid and a Claimant on the same map.

Contains the player/GM split (a sheet vs a board — there are only two shapes and there will not be a third), the mode/scale/seat model, ranked action tiers, and 21 numbered laws meant to settle layout arguments. §10 is the full Director's-console design: running a session and recording it are one act, the four-source corpus that co-writing reads from, and the always-present GM-only log bar. §11 is the division of labour, checked against the shipped `gamesystems/sf2e/` tree — **sf2e already implements MAP, persistent damage, flanking, off-guard, conditions, degree of success and initiative, so never rebuild those**; what only we can build is the homebrew layer, which §10.4 therefore says to automate hardest. §12 indexes sixteen settled questions so they don't get re-litigated. Read it before adding anything to the console.

Added ten condition articles to the local (gitignored) `reference/srd/` mirror to ground this — Clumsy, Drained, Encumbered, Enfeebled, Fatigued, Quickened, Sickened, Slowed, Stunned, Stupefied — which the original mirroring pass never gave their own file. Cross-referenced from the two relevant entries in `data/campaign/open-questions.json`, which stay `status: open` — a proposal isn't a decision.
- `design/design-layers.md` — **a standing methodological commitment (2026-09-06), and it governs the other design docs where they conflict with it.** Build and validate the pure-SF2E baseline FIRST, then add this campaign's own systems on top in layers: Layer 0 pure SF2E → Layer 1 the scale interface → Layer 2 the campaign economy → Layer 3 Resonance/Bleed/Anchors. The reason is attribution of failure: if everything is built at once and a fight isn't fun, you cannot tell which system caused it. Includes the **removability test** (a layer is a real overlay only if deleting it still leaves a playable game — Resonance and Bleed both pass, the scale interface deliberately doesn't) and the rule that encounters are authored as defensible pure-SF2E encounters before Resonance is allowed to change what a pilot may do inside them. Also: `design/ui/` should be able to run a Layer 0 fight before it shows a Resonance band.
- `design/npc-social-intel.md` — the **Character Card**, a theatre-of-mind popup for a scene's NPCs, written 2026-09-06 to answer a real gap in `ideas/entries/in-scene-character-portrait-frames.json` (still `new`). Splits into two tracked things per NPC: **Facts** (permanent, GM-authored, hidden until a reveal trigger fires, then known everywhere that NPC appears for the rest of the campaign — Law 11 applied to a person) and **Attitude** (SF2E's real five-step Hostile→Unfriendly→Indifferent→Friendly→Helpful scale, not an invented one). **Correction worth knowing:** the brief asked for "crit fail, fail, neutral, succeed, crit succeed" — SF2E's real degree of success is four tiers, not five; "neutral" already exists as Failure's silent no-effect outcome on real actions like Make an Impression and Request, checked and cited in the doc. The outcome table for leveraging a known Fact reuses Request's real crit-success/success/crit-failure text plus Coerce's actual grudge mechanic (a real week-long resistance bonus) for a misapplied Fact on a crit fail — nothing invented, all cited. `npc.schema.json` gained a `socialProfile` field. Feeds directly into the already-`accepted` `dialogue-management-panel` idea, which now has a standing reference to read from instead of starting cold each scene.
- `design/resonance-and-bleed.md` — a design investigation of the campaign's two signature homebrew tracks, written 2026-09-06 at the user's request to stress-test them. **Read before changing either.** Findings in brief: Resonance's power-as-permission principle is the strongest decision in the design and shouldn't be traded away; but the measured band spread is **5.7x total combat contribution** from Dead Weight to Absolute before ability tiers count (7/12/24/40 actions — arithmetic in §2, nobody had run it), and "most of the campaign is played at 2 actions" costs more than it looks in a system architecturally built for three. Bleed is the weaker half: **four inflows, one undefined outflow, and only one threshold across ten points**, so points 1-9 do nothing and berserk arrives on a schedule rather than as a managed risk. Six new open questions came out of it (`bleed-intermediate-thresholds`, `bleed-recovery-sinks`, `two-action-default`, `resonance-band-spread`, `suppression-intent-vs-pattern`, `hero-points-vs-berserk`), and the two pre-existing ones (`bleed-visibility`, `ratio-publication`) now carry recommendations. The doc is analysis, not decisions — **but check `open-questions.json` for current status rather than trusting this line: as of 2026-09-13 `two-action-default`, `resonance-band-spread` and `bleed-visibility` have since been resolved, while `bleed-intermediate-thresholds`, `bleed-recovery-sinks`, `suppression-intent-vs-pattern`, `hero-points-vs-berserk` and `ratio-publication` remain open.**
- `design/campaign-arc.md` — everything design-level that's emerged since the original pitch: the 1950s tone pivot, the 8-level arc shape, theme statement, evolving mechanics threads not yet locked into `data/campaign/config.json`. This is the living design doc; update it as the campaign keeps growing. **Contains a standing design principle (2026-09-06, "penalties cost risk, never choice"): a drawback should shrink a character's menu of options as little as possible and raise the stakes of playing them instead** — a permanent tax on choices (fewer slices, fewer actions, forever) is the wrong shape regardless of size; a dynamic, recoverable, player-managed risk (lower HP that only bites in a specific dangerous circumstance) is the right one. Checked and confirmed clean against Resonance's bands, Frame damage's action caps, and the Exhaustion track — all already dynamic states, not menu reductions. ## Schema architecture

- `data/schema/common/sf2e-common.schema.json` holds shared SF2E building blocks as `$defs` (proficiency ranks, ability modifiers, saves, skills, speed, strikes, spellcasting, conditions, feats, etc.) — referenced via `$ref` from the entity schemas below rather than duplicated. It's pure SF2E mechanics; campaign-specific concepts (Resonance, Anchors, Bleed) never belong in it.
- **`pcStatblock`** (in sf2e-common) = the full player-character sheet shape. Used by both `kid.schema.json` and `frame.schema.json`, since a Frame is explicitly built as "a full PC using a standard SF2E class" (design bible) — same underlying shape, different fixed level and campaign overlay.
- **`combatStatblock`** (in sf2e-common) = the monster/NPC stat block shape (flat AC, authored skill mods, no chargen fields) — different from a PC on purpose, per GM Core's own creature-building rules. Used standalone by `creature.schema.json` (Claimants, any other monster) and optionally embedded as `npc.schema.json`'s `statblock` field for the rare NPC that needs to fight.
- `subsystem.schema.json` — GM Core-style victory-point subsystems (Victory Points, Influence, Research, Chases, Infiltration, Hacking, or homebrew). One shared shape (pools, obstacles, thresholds) plus a `subsystemSpecific` bag for what genuinely doesn't generalize (Hacking's DC-modifying vulnerabilities, Infiltration's objective/obstacle hierarchy and Edge Points, Chases' per-obstacle point reset). Don't force a Hacking or Infiltration instance into the plain-pool shape if it isn't one — check `subsystemSpecific` first.
- `challenge.schema.json` — lighter-weight than a subsystem: one or a few DC'd checks with no persistent point pool. Fits Ground Role checks, Anchor Time scenes, one-off skill gauntlets.
- `encounter.schema.json` — a combat encounter's participant list and XP-budget inputs, separate from challenge/subsystem since it uses SF2E's level-relative XP math (`reference/tables/encounter-and-rewards-math.json`) instead of DC'd checks.
- None of this is validated by tooling yet (see ROADMAP.md #1) — treat the schemas as the contract to hand-conform data files to, and keep new fields flowing back into `sf2e-common` when two entity schemas would otherwise duplicate the same shape.

## Conventions

- One JSON file per entity, filename = `id` field (kebab-case), e.g. `data/npcs/commander.json` has `"id": "commander"`.
- Every data file has a `"$schema"` field with a relative path to its schema in `data/schema/` — most editors (VS Code included) will validate and autocomplete against this automatically.
- `null` means "not yet decided," not "empty/unused." A lot of this document is deliberately unresolved — see `data/campaign/open-questions.json` and `data/campaign/naming-placeholders.json`. When a field is null because of a tracked open question, it carries an `openQuestionRef`/`namingPlaceholderRef` pointing at the relevant entry.
- Cross-references between entities are plain string ids (e.g. a kid's `framePilotedRef`), not nested objects — keep entities independently loadable, since that's how they'll eventually map to separate Foundry documents.

## Rules Reference

`reference/srd/` mirrors the SF2e SRD (Galaxy Guide, Player Core, GM Core, Alien Core minus Pact Worlds) — every procedural/mechanical rule, not the item/spell/creature catalogs. Check it before writing anything that leans on specific SF2e mechanics: Frame ability-band assignments, GM adjudication calls, Claimant stat blocks, encounter design, skill DCs. It's more reliable than general knowledge of the system, since exact numbers and wording matter here. See [reference/README.md](reference/README.md) for full scope, structure, and a note on a few files with intentional content overlap. `reference/tables/` has the same information pre-extracted into plain numeric JSON for programmatic use.

One confirmed gap as of the last check: no numeric Elite/Weak adjustment deltas were found anywhere in the mirrored GM Core/Alien Core text — see `adjustment` field notes in `sf2e-common.schema.json`'s `combatStatblock`. Treat any elite/weak numbers as a GM judgment call, not a verified rule, unless this note has been updated after finding the real table.

## Local Foundry source trees (not in git)

Two large reference trees live at the project root, both **gitignored** — same policy as `reference/`, all three are excluded in `.gitignore` because they're bulk third-party/mirrored material, not this project's own content:

- `gamesystems/sf2e/` — the official Foundry VTT "sf2e" system package (v1.4.1, built off the pf2e codebase — matches the design bible's note that SF2E runs on PF2e's engine). Readable parts: **`template.json`** (~18KB, the Actor/Item data model), **`packs/`** (29 compendium packs — LevelDB, not plain JSON; already extracted once, see below), `lang/en.json`, `templates/` (Handlebars sheets). `sf2e.mjs`/`vendor.mjs` are bundled but beautified (not minified) — directly readable.
- `foundryvtt/` — full Foundry VTT v14.367 application source, **unminified** under `client/`/`common/`, minified under `dist/`, at `foundryvtt/Foundry Virtual Tabletop/resources/app/`.

**Already dug into** — see [design/foundry-technical-reference.md](design/foundry-technical-reference.md) for the condensed, cited findings (file:line for the unminified parts) before re-deriving anything from these trees: file I/O and the module write-back mechanism, every relevant Foundry v14 document schema (Scene's `Level` split, JournalEntryPage, Playlist, etc.), the sf2e Actor/Item data model (including the PC-vs-NPC asymmetry — NPCs store flat totals, PCs derive everything from embedded Items), the `@Check`/`@Damage`/`@Template` inline syntax with real examples pulled from the packs, and the ApplicationV2/hooks/module-manifest APIs. Re-verify against the source trees directly only for something not already covered there, or if targeting a different Foundry/sf2e version.

## Foundry module

`module/blank-inheritance/` is the actual module (see its own [README](module/blank-inheritance/README.md)) — campaign JSON and module code ship together, pushed to the Foundry server as one unit via `tools/module-sync/` (or WinSCP by hand). Consolidated here 2026-09-04/05 from the original `foundry/blank-inheritance/` location (GitHub issue #71) — the manifest `id` deliberately stayed `blank-inheritance`, since every deterministic-id derivation and golden test fixture is keyed to that id. The consolidation briefly renamed the directory itself to something else too, which turned out to be invalid — Foundry's real package loader hard-requires the directory name to exactly match the manifest `id`, rejecting the module outright otherwise (found live 2026-09-05, after it silently broke the module on the server for about a day). Renamed back to match; now enforced by an automated test (`test/tier0-architecture.test.mjs`). Design and rationale: [design/foundry-module-design.md](design/foundry-module-design.md) (now includes a **Safety** section on why world-document writes must go through Foundry's Document API, never raw file access — grounded in real source, learned during the 2026-09-04 server migration). See that doc's §9 staged delivery plan before starting implementation, and don't jump straight to the director's panel / cold-open stages before the core push pipeline works. Stage 1 (deterministic IDs, npc + character Actor generation, Scene with tokens, validation-by-reread) is **built and verified against a live Foundry instance** — 15/15 checks passed 2026-08-22. The production-line roadmap (module build-out, the phone/UI systems, the Claude-to-Foundry content pipeline) is tracked as GitHub epics #102 and #118, milestone "Foundry Module."

**[design/testing-strategy.md](design/testing-strategy.md) is required reading before writing any module code.** It's a standing policy, not a suggestion: pure logic lives in `scripts/core/` and may never touch Foundry globals; the adapter layer stays thin; contract tests verify our output against the local `gamesystems/sf2e/` and `foundryvtt/` trees so a system upgrade fails loudly instead of silently. It also records verified gotchas (template.json inheritance, its partial Item coverage) that will cost real time to rediscover.

## Working on this project

- **Don't resolve open design questions unilaterally.** They're listed in `data/campaign/open-questions.json` because they're the user's creative calls (tone, structure, character agency), not implementation details. Surface them when relevant; update a question's `status`/`resolution` and the fields that reference it only once the user actually decides.
- **Don't invent the six kids/Frames' names, classes, or Anchors.** Character creation is collaborative creative work with the user, not something to fill in to make the roster look complete.
- **Mechanical/numeric content is NOT locked. This line used to say it was; that was wrong and was corrected 2026-09-13.** **Resonance and Bleed are both flagged NEEDS REWORK** — not functional, interesting or playable as written (`data/campaign/config.json` carries the flag on both blocks; `design/resonance-and-bleed.md` opens with it; `open-questions.json#resonance-playability` and `#bleed-playability` track them). **The five ground roles are UNDER REVIEW and may be removed entirely** (`open-questions.json#ground-roles-viability`) — two of them only function when a Frame is on the field, and Umbilical Control describes a player spending their action to top up someone else's resource, which is not agency. Time Economy and Contact Pool are still written as concrete rules, but treat the whole mechanical layer as provisional rather than settled. **The standing requirement, from Ingram 2026-09-13: this is a heavily modified SF2E campaign first — every player must have real agency over their own role and actions, and nothing should stray from what makes a good SF2E table experience, however close the design gets to the genre fantasy.**
- The Foundry sync/module work now has a real design (see above) and is no longer purely hypothetical, but implementation still hasn't started — check with the user before writing actual module code rather than assuming the design doc is a green light. The encounter simulator (ROADMAP.md #3) remains untouched and long-term.
- **Every feature ships with an automated test, in the same commit.** Not "after," not "when there's time" — a feature without a test isn't finished. This is a direct, explicit instruction from the user ("every feature we build needs an automated test to prove that it's still working three versions from now"), grounded in the observation that projects like this one live or die on sustainable code practice. See [design/testing-strategy.md](design/testing-strategy.md) for the tiers, the tooling choice (`node --test`, zero dependencies on purpose), and the rules. Every bug found becomes a regression test at the moment it's fixed.
- **Check `ideas/entries/` before starting speculative new work.** A lot of forward-looking scope (asset pipeline, mech classification, audio system, UI panel, antagonist structure, etc.) is already captured there with a real status — don't re-propose or re-decide something that's already `accepted` there, and don't start building something still sitting at `new` without checking whether it's actually been prioritized.
